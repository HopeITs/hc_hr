## 1. ملخص العمل

### ما كان عليه الوضع

كان العمل على موديول التوظيف يجري **على فرعين متوازيين لا يعرف أحدهما بالآخر**:

- **`recruiting-phase-1.1`** — وثائق القرارات وطبقة الصلاحيات والنطاق (المهمة 1 والمهمة 4 من خطة التنفيذ).
- **`rms-main`** — مخطط قاعدة البيانات الكامل: 6 migrations بـ33 جدولاً، و32 موديلاً، و8 Policies، وملفا اختبار.

الفرع الثاني تفرّع **قبل** أول commit للوثائق، فلم تصله القرارات الـ48 إطلاقاً. ولأن الـ Policies تحتاج طبقة تفويض لتبني عليها، كُتبت طبقة ثانية مستقلة من الخطة العامة. النتيجة: **خمسة ملفات بنفس المسار والاسم وبمحتوى مختلف كلياً**، من بينها migration بنفس اسم الملف حرفياً.

### ما تمّ إنجازه

1. **دُمج الفرعان** — 7 ملفات متعارضة، حُلّت بالمنطق لا بـ`--ours` أو `--theirs`.
2. **وُحِّدت طبقة التفويض** — بقي النموذج المبني على الهيكل التنظيمي، وسقط النموذج المبني على أدوار جديدة.
3. **حُوِّلت الحالات والأنواع إلى أعداد** (`unsignedTinyInteger`) تطبيقاً للقرار `D6`، مع 14 كلاس enum بالقيَم المجمّدة.
4. **أُصلحت ثغرة صلاحيات حقيقية** كانت ستظهر يوم النشر فقط.
5. **أُعيدت كتابة اختبارات التفويض** لتختبر النموذج المعتمد: 18 اختباراً تنجح.
6. **نُفِّذت الـ migrations على قاعدة البيانات** وتُحقِّق منها حيّاً على بيانات حقيقية.

## 2. القرارات المعمارية الحاكمة

### 2.1 التفويض ثلاث طبقات لا طبقة واحدة

هذا أهم مفهوم في الموديول. أي سؤال «هل يستطيع فلان أن يفعل كذا» يُفكَّك إلى ثلاثة أسئلة مستقلة، **وتُفحص كلها في كل مرة**:

| الطبقة | مصدرها | تجيب |
|---|---|---|
| **الصلاحية** | الدور (Spatie) | *ماذا* يفعل |
| **الأهلية** | `job_levels.grade` للمنصب | هل يحق له *التقديم أصلاً* |
| **النطاق** | المنصب في الهيكل | *أي* الطلبات طلباته |

حيازة صلاحية بلا النطاق الذي يقابلها **لا تمنح شيئاً**. والـ Resolver **يفشل مغلقاً**: من لا يستطيع تحديد نطاقه يأخذ `RecruitmentScopeType::None` — لا «كل شيء».

### 2.2 النطاق من الهيكل التنظيمي لا من أدوار جديدة

الفرع الآخر أضاف أربعة أدوار نظام: `hr-director` · `program-manager` · `project-manager` · `finance`. **حُذفت كلها.**

السبب (`D7` و `D26`): الدور يُمنح ويُسحب يدوياً، بينما المنصب يتحرّك من نفسه. ترقية موظف تؤهّله في اليوم نفسه، ونقله عن منصب إداري يسحب الأهلية — بلا تدخل مسؤول نظام. البيانات تدعم هذا: `direct_manager_id` معبّأ في **153 من 155** منصباً فعّالاً.

ودور `finance` تحديداً **ممنوع بالقرار `D29`**: الموافق المالي **شخص لا وظيفة**. إنشاء دور بهذا الاسم يحوّل كل حامليه إلى الموافق المالي للمنظمة — وهو بالضبط ما وُجدت صلاحية `approve-finance` لمنعه.

### 2.3 صلاحيتان تُقرآن من المنح المباشرة فقط

```
recruitment-requests.approve-finance
recruitment-requests.submit-without-manager
```

هاتان تجيبان «هل هذا الإنسان بعينه هو المقصود؟». تُنشآن كأي صلاحية وتظهران في واجهة Access Management، لكن **لا يحملهما أي دور إطلاقاً** وتُقرآن من `model_has_permissions` مباشرة (`D27`).

آلية الحماية مركزية: `AccessPermissionCatalog::roleGrantableNames()` تطرح `config('access-control.never_granted_to_roles')`، **وكل منح جماعي يمرّ بها**.

### 2.4 مسار الموافقة ثلاث خطوات

```
مُقدِّم الطلب
   ▼  موافقة المدير المباشر   (موافِق واحد — D16)
   ▼  المدير المالي الأول      (مركزي وإلزامي دائماً)
   ▼  HR المحافظة             (حسب خريطة الإسناد — D21)
Approved
```

`HR-SYR` والرئيس التنفيذي **خارج المسار** (`D13`) — يراقبان ولا يوافقان إلا حين يكونان فعلاً صاحبَي الدور التنظيمي في ذلك الطلب.

**لا توجد حالة `Blocked`** (`D17`) ولا خطوة تصعيد ولا `approver_slot`.

### 2.5 خريطة إسناد HR تُقرأ في الاتجاهين

حلب فيها 46 منصباً ولا يوجد من يحمل دور `HR-ALP`. لولا الخريطة لتوقّف كل طلب حلبي يوم الإطلاق.

```php
// config/recruitment.php
'governorate_hr' => [
    'map' => ['ALP' => 'HR-SYR', 'TAR' => 'HR-LAT'],
    'default' => 'HR-SYR',
],
```

**الاتجاه الثاني ضروري** (`D42`): طرطوس مُسنَدة لـ`HR-LAT`، فلو بقي نطاقه اللاذقية وحدها لوصله الطلب ثم فشل عند فحص النطاق — يُسمّى موافِقاً ولا يستطيع الموافقة.

### 3.4 تحويل الحالات إلى أعداد

نمط المشروع (`D6`): `bensampo/laravel-enum` بقيَم `int`، تُخزَّن `unsignedTinyInteger`، ويُضاف `'العمود' => 'integer'` إلى `casts()` — **بلا Cast class**، تماماً كما يفعل `LeaveRequest`.

**أعمدة لم تُحوَّل ومقصودة:** `vacancies.status` · `job_posts.status` · `application_forms.status` · `public_recruitment_links.status` · `recruitment_campaign_invites.status` · `hiring_campaigns.link_mode` · `priority` · `volunteer_type` · وكل أعمدة جداول المرحلة الثانية.

> **السبب:** قيَمها لم تُجمَّد في العقد التقني، وتحويلها يقتضي اختراع قيَم. جمِّدها في [`06-technical-contract.md`](docs/recruitment/06-technical-contract.md) **ثم** حوِّلها — وافعل ذلك قبل أن تمتلئ الجداول ببيانات.

**تبقى نصوصاً بطبيعتها:** `request_number` · `phone_normalized` · `color` · `assigned_role` (اسم دور Spatie) · `role_key`.

## 4. ثغرة أمنية أُصلحت

**هذه أهم فقرة تقنية في التقرير.**

`App\Models\Role::booted()` يمنح **كل** صلاحيات الكتالوج تلقائياً لأي دور جديد يكون من `administrator_roles` أو يبدأ بـ`HR-`. وكذلك كانت تفعل migration الصلاحيات الأساسية.

بعد إضافة مجموعات التوظيف إلى `config/access-control.php`، صار الكتالوج يشمل الصلاحيتين الشخصيتين — فأصبح **كل دور HR محافظة جديد يُولد وهو يحمل `approve-finance`**، أي أن كل موظف HR في أي محافظة هو الموافق المالي للمنظمة. نقيض `D27` تماماً.

**لماذا لم يظهر:** قاعدة البيانات الحالية كانت قد نفّذت تلك الـ migration **قبل** وجود مجموعات التوظيف، فلم تُعد تنفيذها. الخلل يظهر **على قاعدة بيانات جديدة فقط — أي يوم النشر.**

**الإصلاح:**

```php
// app/Support/AccessPermissionCatalog.php
public static function roleGrantableNames(): array
{
    return array_values(array_diff(self::names(), self::personLevelNames()));
}
```

وكل منح جماعي يستدعيها. ومعها اختبار انحدار: `test_a_newly_created_hr_role_does_not_pick_up_person_level_permissions` — دور `HR-TAR` جديد يحصل على **19 لا 21**.

> ⚠️ **إن أضفت صلاحية تخصّ شخصاً لا وظيفة، أضف اسمها إلى `never_granted_to_roles` في `config/access-control.php`.** وإن أضفت مساراً جديداً يمنح صلاحيات بالجملة، اجعله يقرأ `roleGrantableNames()` لا `names()`.

## 7. تشغيل المشروع محلياً

```bash
composer install
npm install && npm run build
cp .env.example .env && php artisan key:generate
php artisan storage:link
php artisan migrate
```

> **`php artisan serve` لا يعمل على إعداد Windows هذا** — يقول «Failed to listen» على كل منفذ بينما `php -S` يربط المنفذ نفسه بلا مشكلة. الحل في `server.php` بجذر المشروع:
>
> ```bash
> php -S 127.0.0.1:8000 -t public server.php
> ```
>
> **انتبه:** إن كان `public/hot` موجوداً من جلسة Vite سابقة فاحذفه، وإلا وُجِّهت كل الأصول إلى خادم Vite ميت.

## 8. الوضع الحالي مقابل خطة التنفيذ

خطة التنفيذ الكاملة في [`recruitment-execution-plan-ar.md`](recruitment-execution-plan-ar.md). عمود **مطوّر المرحلة الأولى 2**:

| اليوم | المهمة | الحالة |
|---|---|---|
| 1 | حالات الطلب · الأنواع · Workflow Rules · Permission/Scope Matrix | ✅ **مكتملة** |
| 2 | Permission/Scope Resolver + بداية واجهات Request/Create/Details | 🟡 **الـ Resolver مكتمل · الواجهات لم تبدأ** |
| 3 | Workflow Instance + Approver Resolution + Pending Approvals UI | ⛔ لم تبدأ |
| 4 | Approval Actions + timeline | ⛔ لم تبدأ |
| 5 | Job Post · Form version · Public Link · invitation-only | ⛔ لم تبدأ |
| 6–10 | التحصين · واجهات HR · الإشعارات · QA · النشر | ⛔ لم تبدأ |

**الجاهز فعلاً:** المخطط كاملاً · الموديلات · الـ Policies · طبقة التفويض · الـ Enums · الاختبارات.

**الناقص كلياً:** أي مكوّن Livewire · أي مسار (route) · أي شاشة · خدمة الـ State Machine · خدمة تشغيل الـ Workflow.

```
app/Livewire/   → صفر مكوّن توظيف
routes/         → صفر مسار توظيف
```

## 9. الخطوات التالية الموصى بها

### أولاً — قرارات إدارية حاجزة

**لا تفترض إجاباتها.** سبعة أسئلة في [`05-open-questions.md`](docs/recruitment/05-open-questions.md)، وأربعة منها تحجز شغل الأيام 3–5:

| # | السؤال | يحجز |
|---|---|---|
| `Q17` | هل تُتجاوز المراجعة المالية؟ وهل يمرّ بها `CloseVacancy` و`ClosePosition`؟ | بناء الـ Workflow |
| `Q18` | مسار الرفض بعد قرار المدير: إغلاق، أم إرجاع، أم يختار الموافِق؟ | أفعال الموافقة |
| `Q11` | `CloseVacancy` وحملة نشطة — ومصير من تقدّموا | اليوم 5 |
| `Q12` | من يفتح باب التقديم: يدوي، أم بتاريخ، أم الاثنان؟ | اليوم 5 |

### ثانياً — تعارض حُسم بالقرار D50

مصفوفة الأدوار صحيحة: **HR لا ينشئ طلباً عادياً حتى بدرجة 1 أو 3 أو 5**، ومساره الوحيد Direct Opening. عُدّل D33 والكود وفق D50. نتيجة أهلية الدرجة وحدها لا تعني صلاحية المسار. وأُلغي افتراض حصر المدير بمدينة منصبه؛ D49 يعتمد الشجرة الإدارية للإنشاء مع بقاء D30 للرؤية.

### ثالثاً — بناء تقني

1. **جمِّد قيَم الـ enums المتبقية** (§3.4) وحوِّل أعمدتها — قبل أن تمتلئ الجداول.
2. **خدمة الـ State Machine** — تعرض `markApplied()` و`markFailed()` ولا تسمح بضبط `status` مباشرة (`D9`).
3. **خدمة تشغيل الـ Workflow** — تبني الخطوات الثلاث وتحلّ موافقيها. استخدم `approvingManagerPosition()` و`financeApproverUserIds()` و`governorateHrRole()`، **ولا تستدعِ أي مختصر «هل يستطيع هذا المستخدم فعل أي شيء» بدل `canActOnStep()`** — ذلك يعيد فتح ثغرة الموافقة الذاتية من باب آخر (`D10`).
4. **الواجهات** — كل استعلام عبر `scopeRequests()`، وكل فعل عبر الـ Policy.
5. **معاملتان منفصلتان** عند الموافقة والتطبيق (`D44`): الموافقة قرار بشري تمّ ولا يُمحى لأن عملية تقنية فشلت بعده.
